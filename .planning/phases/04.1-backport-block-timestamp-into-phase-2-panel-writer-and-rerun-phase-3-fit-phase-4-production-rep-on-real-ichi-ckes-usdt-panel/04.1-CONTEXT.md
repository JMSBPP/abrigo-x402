## Implementation Decisions

### Where the fix lives (Phase 2 source vs Phase 04.1 augmentation step)

- **Edit `analysis/src/abrigo_x402/ingest.py` PROVENANCE_COLS directly** to include `timeStamp`. The fix lives where the bug lives. This touches "completed" Phase 2 source, which is acceptable because the bug was a real Phase 2 defect surfaced only by Phase 3 consumption — not a v1.0 spec change.
- **Iter-2 swap-surface invariant** (Phase 6 REPRO-02 `git diff fetch/src analysis/src between Iter-1 and Iter-2`) is preserved because this edit lands BEFORE Iter-2 (Phase 6) even starts. No Iter-2 code surface is touched.
- **No `panel_augment.py` duplicate code path.** Adding a non-destructive augmentation script would create two code paths (original panel + augmented panel) and downstream confusion about which panel is canonical. The clean fix is to make Phase 2's panel writer correct.
- **No formal `02-VERIFICATION.md` amendment.** The Phase 04.1 SUMMARY + this CONTEXT.md document the reopening sufficiently for AF-03 audit; touching `02-VERIFICATION.md` would create cross-phase churn for marginal additional clarity. Claude's discretion: planner may add a one-line "Phase 04.1 reopened ingest.py to add block_timestamp; see commit <hash>" footnote to `02-VERIFICATION.md` if it surfaces during planning, but it's optional.

### Scope guardrail for the ingest.py edit

- **ONLY `timeStamp` + sanity tests.** Add `timeStamp` to `PROVENANCE_COLS = ("blockNumber", "blockHash", "logIndex", "txHash", "contractAddress")` → `("blockNumber", "blockHash", "logIndex", "txHash", "contractAddress", "block_timestamp")`.
- Parse hex `timeStamp` (Blockscout v1 raw format: `0x6a0da972`) via `_hex_to_int` (existing helper) and emit as Polars `Int64` unix-seconds in the output schema. Column name in the parquet: `block_timestamp` (snake_case to match Phase 3 expectation).
- Zero-null invariant: extend the existing `blockNumber` null check to cover `block_timestamp` as well — `df["block_timestamp"].null_count() > 0 → raise ValueError`.
- NO other column additions (`transaction_index`, `gas_used`, anything else).
- NO refactors. NO unrelated test additions. NO formatting churn beyond the minimal edit.
- The plan body MUST enumerate the OUT-OF-SCOPE list verbatim so the executor cannot drift (AF-12 defense).

### Phase 2 panel.py provenance metadata header

- **Update `dataHash` only.** Adding `block_timestamp` column changes the panel parquet bytes → new sha256 → new `dataHash` in the PANEL-02 header. Other PANEL-02 fields (`chainId`, `contractAddress`, `blockRange`, `fetchTimestamp`, `gitCommit`) stay correct as written by the existing `provenance.with_header` API.
- The new `dataHash` propagates naturally into the new Phase 3 `run_id` (derivation: `sha256(dataHash + gitCommit + tick_version)[:12]`). The Phase 4 production rep against this new fit_report will therefore land in a different run directory than the synthetic `0afc6af38e24`.
- NO new `panel_schema_version` field. The PANEL-02 schema stays at v1 implicitly. Adding `block_timestamp` is a column-additive change, not a schema break.

### Rerun output disposition (Claude's Discretion default, captured for downstream agents)

- **Keep both run_ids.** Synthetic `data/fits/ichi/0afc6af38e24/` stays archived as "methodology-validation evidence" (the architecture's end-to-end correctness was demonstrated on a controlled-properties substrate). The new real-data `<run_id>` becomes the canonical Phase 5 input.
- Add a one-line `data/fits/ichi/0afc6af38e24/README.md` noting: "Methodology-validation substrate (synthetic-stacked Hawkes η=0.5). Superseded by `<new-run-id>` for v1.0 publication."
- NO deletion of `0afc6af38e24` — would lose audit history of the synthetic-substrate validation path.

### timeStamp column form (Claude's Discretion default, captured)

- Column name: `block_timestamp` (matches Phase 3 expectation verbatim — `swaps.get_column("block_timestamp").cast(pl.Float64).to_numpy()`).
- Type: Polars `Int64` unix-seconds (matches `blockNumber` pattern; cast at ingest time via existing `_hex_to_int` helper).
- NO raw hex preservation. NO downstream decode. Numeric at ingest.

### 04-VERIFICATION-pre.md amendment shape

- **Append "04.1 Real-Data Rerun" section to existing 04-VERIFICATION-pre.md.** The original 18-row grid + frontmatter (`verification_pass: true`, `quarto_skipped: true`) stays intact as historical record of the synthetic-substrate run.
- New section documents the rerun: new run_id, real-data BIC winner, real-data four-condition gate verdict, real-data divergence_flag value, real-data char_func_source.
- Frontmatter gets **three new fields** appended below the existing two:
  - `real_data_rerun_run_id: <new-id>` (machine-readable pointer to the canonical Phase 5 input)
  - `real_data_rerun_passed: <bool>` (boolean signal that the rerun produced a valid `fit_report.json` + `gate_report.json` + (strip or strip_degenerate) artifact set)
  - `substrate_substitution_resolved: true` (explicit closure of the original substrate-substitution caveat)
- The three fields are individually greppable so Phase 5 can consume them at parse time.

### Synthetic-vs-real reconciliation

- **Side-by-side comparison table** in the appended section: 2 columns (Synthetic substrate `0afc6af38e24` | Real panel `<new-run-id>`) × ~6 rows (firing_condition, BIC winner with delta, gate condition pass count, divergence_pct, char_func_source, strip emission path).
- The comparison itself IS load-bearing methodology-validation evidence for Phase 5 — explicitly demonstrates the architecture works as designed on data with known properties (synthetic) AND on data with unknown properties (real).

### Divergence policy (if real-data gate verdict differs from synthetic)

- **Real-data is canonical for v1.0 publication.** If real-panel produces e.g. `firing_condition: null_convex` (no convex-dominance) while synthetic produced `firing_condition: null` (gate passed), real wins. Phase 5 PDF cites the real-data verdict, NOT the synthetic one.
- The divergence is itself a documented finding. Phase 5 narrative must explicitly frame it: "methodology works as designed on the synthetic data with known Hawkes properties; the real economic process exhibits / does not exhibit convex-dominance condition X." That divergence IS the v1.0 scientific result, whether positive or null.
- If real-panel fires HEDGE-05, the v1.0 deliverable IS the null-result PDF — exactly the case the entire Phase 4 architecture (auto-firing template, 4 firing conditions, Quarto render) exists to handle.

### Phase 5 unblocking

- Phase 5 PDF reads `data/fits/ichi/<real-run-id>/` for the canonical v1.0 data. Synthetic run is referenced in the methodology section only (not the headline result).
- The Phase 5 deliverable must explicitly cite the real-data BIC winner, gate verdict, divergence_pct value, and char_func_source — NOT the synthetic values.
- `substrate_substitution_resolved: true` is the machine-readable signal that Phase 5 can start.

### Claude's Discretion

- Whether to add a one-line footnote to `02-VERIFICATION.md` documenting the Phase 04.1 reopening (optional; planner decides during planning).
- Exact wording of the `data/fits/ichi/0afc6af38e24/README.md` archival note.
- Whether to expose a CLI flag `--require-block-timestamp` (default true) on `cli.py fit` for forward-compatibility; or just let the schema-required `block_timestamp` enforce via Polars cast (probably the latter — less ceremony).
- Whether the augmented panel parquet replaces the existing real-data parquet in place (overwrite) or writes to a new path with the new `dataHash` suffix (e.g., `67378253_67896653_v2.parquet`). Probably overwrite — the original was always broken and there's no audit reason to preserve it.
